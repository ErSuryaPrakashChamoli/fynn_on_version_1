# Employees

## Reporting columns are written only by ReportingLineService
Since 2026-09-15 nothing writes superviser_id/manager_id/cluster_id/business_head_id directly. The Employee form has ONE "Reports To" select (not a column): CreateEmployee::mutateFormDataBeforeCreate() derives the four columns via columnsUnder(); EditEmployee unsets it and calls ReportingLineService::reportTo() in afterSave() (page runs in a DB transaction). The Transfer Employee action, HierarchyReassignmentService::transfer()/reassign() and EmployeeImporter (reports_to emp_id, falling back to legacy superviser_id then manager_id) all go through the same service.

reportTo() validates the boss (active, strictly senior; Business Head/Admin report to nobody; everyone else needs a boss, a Cluster Manager only once a Business Head exists), re-fills every descendant from the tree, never touches reporting_date, and writes a history row for every employee whose columns changed — exited ones too since 2026-11-14 (their cases still disburse after they leave, and ReportingTimeline rebuilds past months from these rows; their exit row is left open). The effective date is what every month figure keys on, so set it to the real date of the move. It always runs on edit save, so saving an employee also tidies drifted columns under them. A designation change is dated with ReportingLineService::recordDesignationChange() (a 'designation' history row) so earlier months keep the old designation. Only the importer (and a correction on an exited employee's form) still re-slots direct reports on a designation change; on screen promotions need the team handed over first (see below). Covered by tests/Feature/ReportingLineChangeTest.php.

## Employee dropdowns come from the Employee Setup lists, never hardcoded arrays
Since 2026-09-28 Designation, Position, Target Category, Cost Center, Unit and Role are admin-managed (sidebar "Employee Setup", Admin only). Models use App\Models\Concerns\IsEmployeeOption: options()/optionsIncluding()/labelFor(), delete blocked while an employee holds the value. Labels are swapped against columns: Designation model -> employees.position (stored by NAME, rename cascades to employees); Position model -> employees.designation (id = DESIGNATION_* code; is_system rows can be renamed, never deleted; admin-added positions have designationRank 0, i.e. outside the reporting tree). TargetCategory/CostCenter/Unit store an immutable generated `code`; the target comes from TargetCategory::targetAmountFor() (target_amount, else numeric code). RoleResource::SYSTEM_ROLES are role names checked in code — never renamable/deletable; add to it when code starts checking a new role name. Covered by tests/Feature/EmployeeSetupListsTest.php.

## Employee Setup lists: Active toggle and dependency-aware delete
Since 2026-09-28 every Employee Setup list (and roles) has is_active. Forms offer only active options via optionsIncluding()/activeOptions() (the value already on the record stays selectable); options()/labelFor() still cover inactive ones for display. Delete goes through App\Filament\Actions\DeleteWithDependenciesAction (action name 'delete'): if employees/users still hold the option, the pop-up lists them with Edit links and a required "Move them to" select, then moves them (IsEmployeeOption::moveEmployeesTo / RoleResource::moveUsers) and deletes in one transaction. Move targets: other active options; Position only to out-of-tree positions (rank 0); Role never to hierarchy roles. Test trap: Role's guardable-column list is cached before the is_active migration, so Role::create(['is_active' => false]) drops the flag in tests — use forceFill.

## Leaving, promotion/demotion and target change need nothing attached; moving needs only the team handed over; all are dated
Since 2026-11-14 (decided with the user; moving relaxed 2026-11-16). EmployeeDependencyService defines "attached": active direct reports, open customers they own (JourneySlaService::activeCustomersQuery on assign_to), open assigned leads and leads (not converted, latest status not in CustomerAssignment::CLOSED_FOLLOW_UP_STATUSES), pending/active delegations. Finished work (disbursed/dropped customers, converted/closed leads) is deliberately NOT handed over — achievement and lead reports credit whoever held it. Hand-overs go through the owning services (ReportingLineService, CustomerReassignmentService, CustomerAssignmentService, CustomerJourneyDelegationService).

Leaving: only EmployeeInactivationService::inactivate() (Edit page "Mark Inactive", inactivity-ticket Approve). exit_status on the Employee form is disabled + not dehydrated while active (EditEmployee also unsets it); it can still bring an exited employee back or fix exit_date. exit_date required, never future, never before doj; closes open reporting-history rows and writes the 'exit' row.

Moving (user decision 2026-11-16, replacing "moves with nothing attached"): EmployeeDependencyService::SCOPE_MOVE (moveDependencyCounts()); leaving and Change Position / Target keep SCOPE_LEAVE (everything). The TEAM never moves with them: direct reports are handed over to a new boss first and keep their own work. A CALLER takes all their open work along (customers, assigned leads, leads), so a caller moves straight away with no dependency step. ANYONE ABOVE A CALLER takes along only what they created — customers.employee_id, leads.created_by, customer_assignments.assigned_by = them; open work somebody else created and gave them (incl. admin-distributed assigned leads, assigned_by null) is listed in the step and handed over. Live delegations are never asked about on a move; they run on. Nothing taken along is reassigned; the new boss sees it from the effective date, and past months stay with the old team via the dated history rows. leads.created_by (added 2026-11-16) is set by Lead::booted() creating = signed-in employee (null for an Admin without one; employee_id when nobody is signed in); a hand-over (moveOpenLeads) changes employee_id only. Leads older than the column were backfilled with their holder — no creator was recorded before. EmployeeTransferService::transfer() ("Transfer Employee", TransferEmployeeAction) and ::reassign() (Flexible Reassignment on ListEmployees) refuse while anything in SCOPE_MOVE remains; reassign() ignores direct reports moved elsewhere in the same batch and runs rows lowest level first. The Edit form's Reports To (EmployeeResource::moveProblem) and the importer's "Move only the employee" use the same check. EmployeeDependencyStep and the hand-over methods take the $scope so the step lists and hands over only what stays behind. Full Cluster Transfer (HierarchyReassignmentService::transfer) is the deliberate exception — it moves whole teams. HierarchyReassignmentService::reassign() itself stays unchecked (tests call it directly); UI paths must go through EmployeeTransferService. The importer still calls reportTo() directly.

Promotion, demotion and target category change (since 2026-11-16, decided with the user): only EmployeePositionChangeService::change() ("Change Position / Target", ChangeEmployeePositionAction, action name 'changePosition'). Refused while anything is attached, same as a transfer — the pop-up is the dependency step first, then reopens on position / Reports To / Designation / Target Category / effective date. The Edit form's Position and Target Category are disabled + not dehydrated while on the rolls (EmployeeResource::isOnTheRolls; EditEmployee also unsets them); exited employees stay editable for corrections. The effective date may not be future, before doj, or before the last recorded line/designation change (designation) or category change (category) — earlier would rewrite that later row.

Target categories are dated like designations: ReportingLineService::recordCategoryChange() writes a 'target_category' history row (old_category/new_category = employees.category codes); App\Support\TargetCategoryTimeline rebuilds the category held on each day (latest segment = today's employees.category, so a column edited without a row applies from the last recorded change; no rows = today's category for all time, the old behaviour). AchievementCalculatorService::categoryTarget($employee, $monthStart, $monthEnd) splits a month by days when the category changed inside it (user decision 2026-11-16: old amount × days before / days-in-month + new amount × days from); every other month keeps the category held in it. Partial-month callers keep the flat PARTIAL_MONTH_TARGET. Any new reader of employee_reporting_history that rebuilds reporting lines must skip ReportingLineService::NON_REPORTING_CHANGES. Not dated: editing a TargetCategory's target_amount in Employee Setup still restates every month for everyone in it; past category changes made before 2026-11-16 left no record (no activity log on Employee) and can't be reconstructed. Covered by tests/Feature/EmployeePositionChangeTest.php.

The pop-ups share EmployeeDependencyStep and re-mount via App\Filament\Actions\ReopenAction (Filament keeps a replaced modal open only if name+context differ — hence the 'pass' context counter; assertActionMounted() fails on exact context, assert mountedActions[0]['name'] instead). The Flexible Reassignment hands over through ListEmployees::clearTransferDependenciesAction() (page method action, args employee + batch) and then replaceMountedAction('transferCluster', ['batch' => ...]) refills the form. Covered by tests/Feature/EmployeeInactivationTest.php, EmployeeTransferTest.php and EmployeeSetupInactivationTest.php.

Unit and Cost Center (HasEffectiveInactivation) no longer have an Active toggle: the Inactivate row action moves the holders first, then records `inactive_from` (the first inactive day); a saving hook refuses is_active=false while anyone holds it. Use wasActiveOn()/scopeActiveOn() for date-sensitive figures. Designation/Position/Target Category/Role keep the plain toggle. Date pickers in these pop-ups use maxDate(now()), not today(): the non-native picker fills a default with the current time, which fails a midnight max. Covered by tests/Feature/EmployeeSetupInactivationTest.php.
