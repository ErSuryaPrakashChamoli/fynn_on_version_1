# Filament Widgets

## Dashboard calendar rows are sized to fit the first screen
User decision 2026-09-27: the whole Dashboard calendar grid must fit in the visible area under the page header. The widget's Alpine fitToScreen() measures the .fc-daygrid-body top against .fi-main-ctn (with the page at rest), divides the remaining height by the week-row count (min 44px) and sets --fynn-calendar-row-h on .filament-fullcalendar (inside wire:ignore, so Livewire morphs keep it), then re-measures the card's bottom once and takes any overflow back off the rows. theme.css uses it as a fixed height (overflow hidden) on .fc-daygrid-day-frame. Trap: a min-height alone did nothing — FullCalendar's own spacing (.fc-daygrid-day-events min-height + 1em bottom margin, number/chip padding) kept rows near 6rem, so the Dashboard-scoped rules zero that spacing. It re-runs on resize and on any grid DOM change (view/month switch). Don't go back to a fixed 5.5rem row on the Dashboard.

## Dashboard calendar is drawn on the server, not by FullCalendar's script
User decision 2026-09-28: the grid and its follow-up chips must appear in one go with the page. With FullCalendar the card sat empty while its 1.4 MB Alpine bundle loaded (x-load), then the chips followed in a fetchEvents round trip — no preload/embedding trick removed that. DashboardFollowUpCalendarWidget now renders the grid in Blade (calendarGrid(), calendarPeriod(), calendarTitle(); state $calendarView month|week|day and $calendarDate; Livewire actions switchCalendarView/showPreviousPeriod/showNextPeriod/showTodayPeriod/selectCalendarDate). The markup keeps FullCalendar class names (fc-daygrid-day, fc-daygrid-day-frame, fc-col-header-cell, fc-button, has-followups, is-selected-day, lead-followup-day-chip…) so the theme's calendar CSS applies; theme.css "fynn-server-calendar" holds the layout rules FullCalendar used to inject. Month shows only the month's weeks with neighbour days blank (fc-day-disabled). The .filament-fullcalendar element carries wire:ignore.self: every re-render (picking a day) otherwise morphs away the --fynn-calendar-row-h that fitToScreen() set on it, and the last week falls below the screen. Chips come from the cached fetchEvents(). Do not reintroduce x-load / FullCalendar on the Dashboard; the separate Lead / Customer Follow-Up Calendar pages still use FullCalendar. $isLazy = false. Lead visibility (AssignedLeadFollowUpCalendarWidget::scopeToVisibleLeadFollowUps) must stay subqueries, never pluck()ed id lists.

## Follow-up calendar day chips are cached per user + month (FollowUpCalendarCache)
ShowsFollowUpOutcomes::fetchEvents() goes through App\Support\FollowUpCalendarCache::remember() (key: version, DB connection + database — /demo has its own DB — widget, user, range; TTL 300s). classify() over a month was ~280 ms of every Dashboard load; cached it is ~1 ms. AppServiceProvider bumps the version on saved/deleted of FollowUp, CustomerAssignment and Lead, so new follow-ups show at once; the TTL only covers time passing (open → missed). A bulk query-builder update()/insert() on follow_ups skips those events — call FollowUpCalendarCache::flush() yourself if it changes dates or subjects.
