# Cashback

## customers.cashback follows the file's live cashback form — never type it
User decision 2026-11-20: the paper cashback "Acknowledgment" voucher is now Customers → Cashback Forms (customer_cashback_requests). Step 4 of the journey has a declaration (customers.cashback_option: none / cashback / expected); the old typed "Cashback Given" input is gone and the Step 4 amount is read-only (dehydrated(false)). CustomerJourneyService::sanction() refuses a disbursed file without a declaration, or with cashback / expected but no live form of that type (CustomerCashbackService::cashbackForDeclaration).

CustomerCashbackService is the only writer. User decision 2026-11-20 (same day): a new cashback can come on a case punched in on any earlier day or month, so a case may carry several forms; only ONE may be pending (pending_manager / pending_admin) at a time. The first form copies the cashback a disbursed case already carried into customers.cashback_before_forms (0 for a case still at Step 4); syncCustomer() sets customers.cashback = cashback_before_forms + every live (pending or approved) form's approved_amount ?? amount — a new form ADDS, a rejection/retrieval takes off only that form. Pending forms already count, so the achievement/incentive maths (which read customers.cashback, MIS cashback first) need no change. cashback_option follows the live forms (cashback wins over expected). The standalone entry point is Cashback Forms → Fill cashback form (also the "Cashback Form" button on the Customers list): pick the case, optionally filtered by disbursal month (CustomerCashbackRequestForm::caseQuery — Customers scope, Step 4 or disbursed, no pending form). The customer page's Cashback section only fills and approves/rejects the pending form; retrieve / change amount / payment live on each voucher. Flow (user decision 2026-11-21): a Team Leader's form goes to the filler's own supervisor — nearest active Manager/Cluster/Business Head above them with an active login (supervisor_employee_id); that supervisor or anyone above them signs it off within SUPERVISOR_TAT_HOURS = 24 (supervisor_due_at), after which canApprove() refuses them and `cashback:escalate-overdue` (every 5 min, plus a demo:run counterpart) moves it to pending_admin with escalated_at and notifies Admin, supervisor and filler. No supervisor with a login → straight to the Admin. A Manager/Cluster/Business Head's form starts at the Admin; the Admin's own is approved at once; the Admin can approve at any stage. Only an unpaid Expected cashback can be retrieved (TL and up on the file's chain) → cashback 0. After approval only the Admin changes the amount (changeAmount, logged with reason); Admin/Accounts record payment (Paid needs mode + date + UTR unless cash; On Hold needs remarks). CustomerEditRequestService refuses the `cashback` field on any case that has a cashback form. Settlement sales_cashback is a snapshot and is not re-synced. Covered by tests/Feature/CustomerCashbackFormTest.php.

## Voucher rows and second payments (revisions)
User decisions 2026-11-21: the voucher shows Manager Name and Cluster Manager Name (snapshot manager_employee_id / cluster_manager_employee_id of the file owner's chain) instead of the paper form's "Floor Manager"; CustomerCashbackRequest::chainSignature() decides each row's signature (filled, signed off as supervisor, awaiting, or "not signed within 24 h"). "Record payment" (Admin or Accounts) sits on the voucher section (key cashbackVoucher), not the page header, and takes a typed paid_by_name (paid_by keeps who recorded it). A cashback paid a second time is REVISED, never re-paid on the same form: CustomerCashbackService::revise() (only on a paid, non-revision original) raises a new form on the same case with revision_of_id / revision_no, voucher_no "<original>/R<n>", same type, required reason, same approval path and TAT; its amount adds to the case total. A UTR can be recorded on only one form. Covered by tests/Feature/CustomerCashbackFormTest.php.
